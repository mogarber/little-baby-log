# Little Baby Log — Architecture

Free, open-source (GPL-3.0) iPhone app for tracking a baby's sleep, feeding,
diapers, pumping, growth, and medicine. Think Huckleberry, minus the paywall.

**Principles:** no servers, no accounts, no analytics, no ads. Data lives on the
device and in the family's own iCloud. Caregivers share a baby via CloudKit
sharing. Designed for one-handed use at 3am: big targets, few taps, haptics.

## Data model (Core Data, defined in code)

`BabyLogModel.model` builds the `NSManagedObjectModel` programmatically (no
.xcdatamodeld). CloudKit rules: every attribute optional or defaulted, no
unique constraints, all relationships optional with inverses. **Additive changes
only** once the CloudKit schema is deployed to production.

**Baby** (`@objc(Baby) public final class Baby: NSManagedObject`)
| attr | type |
|---|---|
| uuid | UUID? |
| name | String? |
| birthDate | Date? |
| createdAt | Date? |
| events | to-many LogEvent, cascade, inverse `baby` |

**LogEvent** (`@objc(LogEvent) public final class LogEvent: NSManagedObject`): one entity
for every kind, with kind-specific optional fields. One entity keeps sharing simple
(share the Baby and its whole graph goes along) and the timeline a single fetch.

| attr | type | used by |
|---|---|---|
| uuid | UUID? | all |
| kindRaw | String? | all (`EventKind.rawValue`) |
| startDate | Date? | all (instant kinds: the time) |
| endDate | Date? | sleep, breastfeed, pump. **nil on sleep/breastfeed = timer running** |
| notes | String? | all |
| createdAt, modifiedAt | Date? | all |
| leftSeconds, rightSeconds | Double = 0 | breastfeed: accumulated (paused) seconds per side |
| activeSideRaw | String? | breastfeed: side currently running, nil when paused |
| activeSideStartedAt | Date? | breastfeed: when active side started |
| lastSideRaw | String? | breastfeed: last side used (for "next side" hint) |
| amountML | Double = 0 | bottle |
| bottleContentRaw | String? | bottle |
| foodName | String? | solids |
| diaperKindRaw | String? | diaper |
| leftML, rightML | Double = 0 | pump |
| weightKg, lengthCm, headCm | Double = 0 | growth (0 = not measured) |
| medicineName, dose | String? | medicine (dose is free text, e.g. "2.5 ml") |
| baby | to-one Baby, nullify, inverse `events` |

All storage is metric. Display units are user prefs.

Running timers are stored in Core Data (not in memory), so they survive app kills
and **sync live to the other caregiver's phone**.

## App (iOS target)

**Config.** `Info.plist` key `LBLCloudKitContainer = $(CLOUDKIT_CONTAINER)`. `AppConfig.cloudKitContainerIdentifier`
reads it (nil if empty or unexpanded `$(`). `PersistenceController.shared` is built from it; `.preview` is in-memory
with `SampleData`. Exposed to views via `@Environment(\.persistence)` (default `.shared`) plus the standard
`\.managedObjectContext`.

**Prefs** (`@AppStorage`): `Prefs.selectedBabyID` (uuid string), `Prefs.volumeUnit` (`VolumeUnit`, default ounces if
`Locale.current.measurementSystem == .us` else ml), `Prefs.unitSystem` (`UnitSystem`, metric if locale metric else imperial). Appearance and battery prefs:
`Prefs.appearanceMode` (`AppearanceMode`, default System), `Prefs.nightStartMinutes` / `Prefs.nightEndMinutes` (minutes
since midnight, default 1140 and 420), `Prefs.dimScreenAtNight` (default off), `Prefs.keepScreenOnWhileNursing`
(default off). See "Appearance and Night mode" and "Battery opt-ins" below.

**Share acceptance.** `AppDelegate` (via `@UIApplicationDelegateAdaptor`) returns a `UISceneConfiguration` whose
`delegateClass = SceneDelegate.self`. `SceneDelegate` handles `windowScene(_:userDidAcceptCloudKitShareWith:)` and
cold-launch `connectionOptions.cloudKitShareMetadata` → `PersistenceController.shared.acceptShareInvitations`.
Info.plist has `CKSharingSupported = YES`, `UIBackgroundModes = [remote-notification]`.

**Sharing UI.** `CloudSharingCoordinator` (`@MainActor`, `UICloudSharingControllerDelegate`): calls
`persistence.share(baby)` then presents `UICloudSharingController(share:container:)` from the top view controller
(not via a SwiftUI representable — that's buggy). `itemTitle` = baby name; `didSaveShare` → `persistUpdatedShare`;
`didStopSharing` → if participant (`isInSharedStore`) `purgeSharedZone`. Calls an `onChange` closure so rows refresh.

**Screens.**
- `RootView`: babies `@FetchRequest` sorted by createdAt; selected = matching `Prefs.selectedBabyID` or first.
  `loadError` → `ContentUnavailableView`. No babies → `OnboardingView`. Else `MainTabView(baby:)`.`id(baby.objectID)`.
- `MainTabView`: tabs Today / History / Trends / Settings. Holds `@State day = startOfDay(now)`, refreshed on
  `UIApplication.significantTimeChangeNotification` and scenePhase active; passes it to `TodayView(...).id(day)` so
  fetch predicates roll over at midnight.
- `TodayView(baby:day:)` — a `List`:
  1. **Active timers** (running sleep / nursing): `ActiveTimerRow` with live clock (`TimelineView` 1s), "Wake up"
     (sets endDate) or "Open" (nursing timer sheet).
  2. **Since last** (`SinceLastView`, 30s refresh): Awake-for / Asleep-for, last feed "2h 10m ago" + "Next: Right"
     (other side of latest finished nursing), last diaper. Section header shows `BabyAge`.
  3. **Quick actions** (`QuickActionsGrid`, 4-col grid of `KindIcon` buttons, `.buttonStyle(.borderless)`):
     Sleep toggles a sleep timer; Nursing creates a running breastfeed and opens `BreastTimerView`; others open
     `EventEditorView` for a new entry. Context menu on every tile: "Log past <kind>" (editor). Diaper context menu
     also has instant Wet / Dirty / Wet + dirty.
  4. **Today summary** (`DaySummaryView`): Sleep, Feeds (+ bottle total), Diapers (wet/dirty), Pumped.
  5. **Timeline**: today's finished events (`EventRow`), tap → editor (running nursing → timer), swipe to delete.
  Toolbar: `BabySwitcherMenu` (only when >1 baby; self-contained: own fetch + AppStorage). `.sensoryFeedback(.success)` on logs.
- `BreastTimerView(event:suggestedSide:)`: big total clock, two large Left/Right tiles each with its own clock and
  play/pause; tap = `toggleSide` + save (so partner sees it live). "Next" badge on suggested side before starting.
  Done = `finishNursing` (or delete if 0s). Discard (confirmation) = delete. On disappear: delete if never started.
- `EventEditorView(baby:target:)` with `enum EditorTarget: Identifiable { case new(EventKind), edit(LogEvent) }`.
  `Form` over an `EventDraft` (`@State`); Save disabled while `validationMessage != nil` (shown as footer).
  Per kind: sleep (start, "Still asleep" toggle, end, duration); nursing (start, L/R minutes, last side; running → start
  + notes only); bottle (amount in user unit, contents segmented); solids (food); diaper (segmented kind); pump (start,
  minutes, L/R amounts); growth (weight — imperial = lb + oz fields — length, head); medicine (name, dose). Notes for
  all. Edit mode adds Delete with confirmation. Numeric input uses a `NumberField` backed by a String `@State` parsed
  with the current locale (TextField(value:format:) only commits on return, and decimal pads have no return key).
- `HistoryView(baby:)`: all events grouped by day, newest first; section header = date + mini summary
  ("Sleep 13h 20m · 8 feeds · 7 diapers", overnight sleep counted using the previous day's events too); kind filter
  menu; "+" menu to log a past entry of any kind; tap to edit; swipe to delete.
- `TrendsView(baby:)`: 7 / 14 / 30 day segmented picker; Swift Charts cards: sleep hours per day, feeds per day,
  diapers per day stacked (Wet / Dirty / Both), bottle volume per day, weight over time (all growth entries). Each card

- `SettingsView`: Babies (edit / add via `BabyFormView`); Appearance; Nursing timer (keep-awake opt-in); Caregivers (`CaregiverRow` per baby: status "Not shared" /

- `OnboardingView(onCreate:)`: welcome, name + birthday, "Start tracking"; footnote about accepting a caregiver
  invite instead (the baby appears once iCloud syncs).
- `EventKind+Style.swift`: `color` (sleep indigo, breastfeed pink, bottle orange, solids green, diaper teal, pump

## Appearance and Night mode

Night is a dim, warm, true-black look for feeding in the dark: a bright screen is the enemy at 3 a.m., and black pixels
cost nothing on an OLED.

**Setting** (Settings > Appearance, an inline picker): System, Light, Dark, Night, "Night on a schedule" (Night between
two times, default 7:00 PM to 7:00 AM, otherwise System). From/To time pickers appear for the schedule. "Dim screen at
night" appears only when Night is possible (the two Night modes), default off, with a `BatteryImpactNote` saying it
saves battery. A footer says widgets and Live Activities follow the system's Light/Dark setting: iOS doesn't let apps
force it.

**Logic (BabyLogKit, `Appearance.swift`, tested in `AppearanceTests`).** Pure and clock-free.
- `AppearanceMode` (`system, light, dark, night, nightSchedule`; raw values are stored, never rename), `canShowNight`,
  `resolved(schedule:at:calendar:) -> ResolvedAppearance` (`system, light, dark, night`), `nextTransition(schedule:after:calendar:)`
  (nil unless scheduled).
- `NightSchedule(startMinutes:endMinutes:)`: minutes of the day, folded into 0..<1440. Active from start (inclusive) to
  end (exclusive), wrapping past midnight when start > end; start == end is an empty window (never active).
  `isNightActive(at:calendar:)`; `nextTransition(after:calendar:)` is the next start or end strictly after `date`, found
  with `Calendar.nextDate(after:matching:)` so daylight-saving changes land on the right wall-clock time.

**Applying it (`App/Support/AppearanceHost.swift`, `.appearanceHost()` on the root of the `WindowGroup`).**
- Resolves the mode to a `ResolvedAppearance` held in `@State` (seeded from `UserDefaults` in `init`, so there is no
  flash at launch). Light/Dark/Night set `.preferredColorScheme`; System sets nil. Night also sets `.tint` to the Night
  accent and `\.appTheme`.
- **No polling.** One `.task(id:)` keyed on mode, schedule, "scene is active" and a clock-change counter: it
  re-evaluates now, then sleeps exactly until `nextTransition`, once, and loops to the following one. Backgrounding
  changes the key, which cancels the wait, so nothing runs in the background; becoming active (and
  `UIApplication.significantTimeChangeNotification`, which bumps the counter) restarts it and re-evaluates.
- **Theme.** `Shared/AppTheme.swift`: `struct AppTheme { isNight }` with `.standard` and `.night`, exposed as
  `@Environment(\.appTheme)` (default `.standard`, which is all the widgets ever see). It holds the palette and the roles
  views ask for: `background` (#000), `surface` (near black, for rows and cards), `raised`, `primary` / `secondary` /
  `tertiary` text (dim warm amber and peach, never white), `accent` (deep warm red-amber), `onColor` (text on tinted
  buttons), `destructive`, `color(for: EventKind)` / `color(for: BreastSide)` (desaturated, dimmed, each kind still its
  own hue), `diaperColors` for Trends. Every accessor returns the stock system value when `isNight` is false, so Light,
  Dark and System look exactly as before. `KindIcon` reads the theme.
- **Applying to screens (`App/Support/ThemeModifiers.swift`).** `themedList()` (List/Form: amber text, hidden scroll
  background, black), `themedScreen()` (ScrollView and the like), `themedForeground()`, `themedSection()` (near-black
  rows), `themedOnColor()` (label on a tinted button), `themedDestructive()`. Each is a no-op in the standard theme, by
  an `if theme.isNight` that adds modifiers only at night. Do NOT put one `.foregroundStyle` on the root instead: an
  explicit foreground style on an ancestor changes stock controls in Light and Dark (a `.borderedProminent` button's
  label turns black). Views that tint or color things themselves use `theme.secondary`, `theme.color(for:)` and so on.
- **Bars (`App/Support/BarAppearance.swift`).** Navigation titles and the segmented picker can't be colored from
  SwiftUI, so Night sets the UIKit appearance proxies and restyles the bars that already exist (it walks the windows'
  views and the view controllers, because on recent iOS the floating tab bar isn't a `UITabBar` in the view tree).
  It does nothing until Night has been shown once in the launch, so Light/Dark/System keep the stock bars. Known limit:
  the system's glass tab bar keeps its own label color for unselected items; the selected one follows the accent.
- **Dimming (`App/Support/ScreenDimmer.swift`).** While Night is showing, "Dim screen at night" is on and the scene is
  active, the brightness is lowered to `min(current, 0.2)` and the person's own level is put back when any of that
  stops (Night ends, the app goes inactive or to the background, the toggle is turned off). If they moved the slider
  meanwhile, their value is kept. It goes through the active window scene's `screen`: `UIScreen.main` is deprecated as
  of iOS 26. iOS also restores the system brightness itself when the app goes away. (The simulator ignores brightness
  writes, so this is verified there only by the state machine, not by pixels.)
- Widgets and Live Activities follow the system appearance, not this setting.

## Battery opt-ins

Battery is a top priority, so anything that costs it is off by default and says so where it is turned on.
- `BatteryImpactNote(_ text, effect: .costs | .saves)` (`App/Views/BatteryImpactNote.swift`): a small battery icon and
  one sentence in the secondary style. Put it directly under the toggle for any setting that costs (or saves) battery.
- **Keep screen on during nursing timer** (Settings > Nursing timer, `Prefs.keepScreenOnWhileNursing`, default OFF).
  `BreastTimerView` sets `isIdleTimerDisabled` to the pref on appear (and when it changes), and always back to false on
  disappear. Note under it: "Keeps your screen on while the timer is open, which uses more battery."
- **Dim screen at night** is the other way around (`.saves`).

## Widgets, Live Activities, and widget actions

Goal: the fastest possible path at 3am. A parent should be able to see "last feed 2h 10m ago · next: Right" and
start nursing on that side **without opening the app**, then manage the running timer from the Lock Screen /
Dynamic Island.

### Targets and shared container
- New target `LittleBabyLogWidgets` (`app-extension`, WidgetKit + ActivityKit), embedded in the app, depends on
  BabyLogKit. Sources: `Widgets/` plus the shared folder `Shared/` (compiled into BOTH the app and the extension).
- **App Group** `$(APP_GROUP_ID)` = `group.$(BUNDLE_ID_PREFIX).littlebabylog`, always on (works in the simulator and
  with free personal teams). Info.plist key `LBLAppGroup = $(APP_GROUP_ID)` in both targets. App gets
  `NSSupportsLiveActivities = YES`.
- Entitlements: `Config/LittleBabyLog.entitlements` = app group only (default). New
  `Config/LittleBabyLog-iCloud.entitlements` = app group + iCloud/CloudKit + aps-environment (what
  `Local.xcconfig.example` points `CODE_SIGN_ENTITLEMENTS` at). `Config/LittleBabyLogWidgets.entitlements` = app
  group. App.xcconfig default `CODE_SIGN_ENTITLEMENTS = Config/LittleBabyLog.entitlements`.
- The Core Data store moves into the App Group container (`<group>/Library/Application Support/`). On first launch,
  if a store exists at the old default location and not the new one, migrate it with
  `NSPersistentStoreCoordinator.replacePersistentStore` (both private.sqlite and shared.sqlite) then delete the old
  files. If the group container is unavailable, fall back to the default directory (never crash).

### Data flow (why the widget never opens Core Data for reading)
- The **app** is the only process that runs `NSPersistentCloudKitContainer`. After every viewContext save and every
  `NSPersistentStoreRemoteChange` (partner's changes arriving from iCloud), `WidgetSnapshotWriter` (app) builds a
  `WidgetSnapshot` for every baby, writes it atomically as JSON to `<group>/widget-snapshot.json`, and calls
  `WidgetCenter.shared.reloadAllTimelines()` (debounced ~1s; skip reload if the encoded JSON didn't change).
- The **widget** only reads the JSON. Live clocks use `Text(timerInterval:)` / `Text(date, style: .relative)`, so
  they tick without timeline reloads. Timeline: one entry now (+ one at midnight), policy `.never`.
- **Buttons in widgets / Live Activities** use AppIntents that conform to `LiveActivityIntent`, so iOS runs
  `perform()` **in the app's process** (launched in the background if needed). That keeps all writes inside the
  app's CloudKit container, so a partner sees a widget-started timer promptly. `perform()` uses
  `PersistenceController.shared` (the app's), applies the action via `WidgetActions` (BabyLogKit), saves (which
  triggers the snapshot writer + Live Activity sync), and returns `.result()`.
- Deep links for things that need UI (bottle amount, editor): `littlebabylog://log/<kind>?baby=<uuid>`,
  `littlebabylog://nursing?baby=<uuid>`, `littlebabylog://today?baby=<uuid>`. App handles them with `.onOpenURL`:
  select that baby, switch to Today, open the editor / nursing sheet.

### Battery
Battery drain from widgets is a known complaint about other baby trackers, so the rules are strict:
- Widget timelines use `.never`. Every time on screen updates itself: `Text(date, style: .relative)` for "ago",
  `Text(timerInterval:)` for running clocks. The app calls `WidgetCenter.reloadAllTimelines()` only when the snapshot
  JSON actually changed (debounced ~1 s, and skipped when equal apart from `generatedAt`). No periodic reloads.
- Live Activities are updated only on real state changes (start, side switch, pause, finish): `LiveActivityPlanner` compares
  the new content state with the current one first and emits no action when they are equal. Clocks tick through `Text(timerInterval:)`. An activity ends as
  soon as its timer finishes or is deleted. No push tokens.
- No background fetch, no `BGTaskScheduler`, no location, no audio sessions, and no polling loops or repeating timers
  anywhere. Everything is driven by events: Core Data saves, CloudKit remote-change notifications, changes to the three
  preferences that are in the snapshot, and entering the background.
- Time since the last feed or sleep ("ago") uses `Elapsed.since`: on iOS 18+ `Text(Date.now, format: .offset(to: date,
  allowedFields: [.day, .hour, .minute], maxFieldCount: 2, sign: .never))`, a `SystemFormatStyle.DateOffset` that the
  system keeps current once a minute with no timeline reloads ("2 hours, 10 minutes", "6 minutes"; no seconds, so it
  neither flickers nor drains). The input is "now" and `date` is the anchor; passing `date` as both gives a constant 0.
  iOS 17 falls back to `Text(date, style: .relative)`. The system picks the wording (wide units, "0 minutes" in the first
  minute); the format style has no unit-width option.
- On a dimmed Always-On Lock Screen (`isLuminanceReduced`) iOS draws the seconds of any ticking `Text(timerInterval:)` as
  dashes once a timer passes a minute, so the Live Activity's total came out as "1:--". `LiveClock` and `NursingTotalClock`
  therefore show whole minutes (`Elapsed.since`, "1 minute") in that state. Paused sides are static text and unaffected.
- Dark mode: widget background is the system background (pure black), tiles use muted tints (about 20% to 50% opacity)
  instead of solid saturated fills, and kind icons are slightly dimmed.

### Live Activity reconciliation
`LiveActivityManager.reconcile(_ trigger:)` (app, `@MainActor`) makes ActivityKit match the running sleep / nursing timers in
the store. The decisions are a pure function, `LiveActivityPlanner.plan(timers:activities:dismissed:isForeground:)` in
BabyLogKit (unit tested); the manager gathers the inputs, performs the returned actions (`end`, `update`, `start`), and
remembers the outcome. Calls are serialized (a chained `Task`), so overlapping triggers can't both start an activity.
- **Triggers**: process launch (`.launch`), every `scenePhase == .active` (`.foreground`, from `LittleBabyLogApp`
  `onChange(of: scenePhase, initial: true)`), every Core Data save on the app's coordinator (debounced 300 ms), every
  `NSPersistentStoreRemoteChange` (a partner's change; debounced, then `await viewContext.perform {}` so the fetch queues
  behind the merge, and the fetch uses `shouldRefreshRefetchedObjects`), entering the background, and after a widget /
  Live Activity intent (`.intent`). No polling, no timers.
- **Foreground-only start**: `Activity.request` only works while the app is in the foreground (push-to-start would need a
  server, which this app doesn't have). `isForeground` is true for `.foreground`, `.intent` (a `LiveActivityIntent` may start
  activities from a background launch), or `UIApplication.applicationState == .active`. When a reconcile wants to start an
  activity but isn't foreground, the timer is *pending*: nothing is started, nothing is remembered, and the next `.active`
  reconcile starts it. So a timer already running at launch, or one a partner started on their phone and that arrived by iCloud
  sync while the app was in the background, gets its Live Activity the moment the app is next opened. Until then there is no
  Live Activity for it; that is an iOS limit. A failed `Activity.request` is also left pending and retried at the next trigger.
- **Updates and ends work in the background** and are applied immediately: when a CloudKit push wakes the app and a partner
  has finished the timer, the activity ends right away. A different timer for the same baby and kind (new event uuid) ends the
  old activity first; the new one waits for the foreground if need be.
- **Identity**: `TimerActivityAttributes.eventID` (the `LogEvent` uuid, optional so activities started by older builds still
  decode) ties an activity to its timer. After a relaunch the activities are still in `Activity.activities` and are re-adopted
  by `eventID` (or by babyID + kind when it's nil). At most one activity per running timer: a second live activity for the same
  timer is ended. Planner input has at most one timer per baby and kind (the newest).
- **Dismissed vs. never started**: per event uuid the app keeps a `LiveActivityLedger` in UserDefaults:
  `liveActivityStartedTimers` (an activity was requested) and `liveActivityDismissedTimers` (the activity ended without the app
  ending it). `activityStateUpdates` is observed for every adopted / started activity; a terminal state the app didn't cause
  (swiped away on the Lock Screen or Dynamic Island, or the system's 8 h limit) records the event as dismissed. An event that is
  "started but has no live activity now" is treated as dismissed too, which covers a swipe while the app wasn't running. A
  dismissed timer never gets another activity; a timer that never got one (not in the ledger) does. Both sets are pruned to the
  timers that are still running.
- Limitations: a Live Activity the system removes while the app isn't running (for example on device reboot) looks like a
  dismissal and isn't restarted for that timer. Starting from the background is impossible without push-to-start. Users who
  turned Live Activities off get nothing (`areActivitiesEnabled`).
- DEBUG builds only (`App/Support/DebugHooks.swift`): launch argument `-lblResetLiveActivities` ends every activity and clears
  the ledger; `-lblInsertTimerInBackground sleep|breastfeed` inserts a running timer from a background context 2 s after the
  app enters the background, to exercise the pending-start path without a second device.

### Implementation notes (where the build differs from the sketch below)
- **Timeline**: one entry now plus one at the next midnight (same data, so "today" counts roll over), reload policy
  `.never`. See "Battery" below.
- `WidgetSnapshot.Feed` has an extra optional `endedAt`: "time since last feed" counts from the end of a nursing
  session, like `SinceLastView`.
- `DeepLink` (parse + build `littlebabylog://` URLs) and `StoreMigration` live in BabyLogKit so they're unit tested.
- `StoreMigration` copies each store into a staging folder next to the destination, verifies baby/event counts match the
  original, moves the `.sqlite` file in last, and only then deletes the old files. On failure the old store stays put and
  the app keeps using it (retried next launch).
- `EventKind+Style.swift` moved from `App/Views` to `Shared/` (the widgets use the same colors and `KindIcon`).
- App-only intent bodies are behind `#if LBL_APP` (`OTHER_SWIFT_FLAGS = -D LBL_APP` on the app target) and implemented in
  `App/Support/AppIntentActions.swift`; each action saves and then runs `AppServices.syncNow()` before `perform()` returns
  (iOS may suspend the process right after).
- Live Activity lifecycle: see "Live Activity reconciliation" above. In short, one activity per running timer, started only
  in the foreground, never re-started for a timer the person dismissed.
- Never put `.fixedSize()` on a `Text(timerInterval:)` in a widget: the widget renders blank.
- Don't interpolate a `Text(date, style: .relative)` into a longer `Text` on Home Screen widgets: it loses the surrounding
  foreground style and renders black in dark mode. Use separate views (`AgoStack`, `AgoLine`). (Lock Screen accessory

## Predictions (free, on-device)

Goal: Huckleberry's "SweetSpot", free and private. Everything runs on the phone from the baby's age and logs;
nothing leaves the device. Always labeled as an estimate: "Estimates from typical ranges and your logs. Not
medical advice."

### BabyLogKit: `Predictions/` (pure, fully tested; no Core Data in the math)
```swift
public struct SleepSession: Equatable, Sendable { public var start: Date; public var end: Date? }   // end nil = running
public struct FeedSample: Equatable, Sendable { public var start: Date; public var kind: EventKind }

public enum PredictionBasis: Equatable, Sendable {
    case typicalForAge          // not enough history yet
    case blended(days: Int)     // age norms + this baby's last N days
    case personal(days: Int)    // enough history that the baby's own pattern dominates
}

public struct AgeNorms: Sendable {             // table keyed by age; documented sources in comments
    public static func wakeWindow(ageDays: Int) -> ClosedRange<TimeInterval>   // e.g. 0-4 wk 35-60 min ... 18-24 mo 5-6 h
    public static func napsPerDay(ageDays: Int) -> ClosedRange<Int>
    public static func feedInterval(ageDays: Int) -> ClosedRange<TimeInterval>  // newborn ~2-3 h, 2-4 mo ~3-4 h, ...
}

public struct SleepPrediction: Equatable, Sendable {
    public enum Kind: Sendable { case nap, bedtime }
    public var kind: Kind
    public var window: DateInterval          // e.g. 2:10-2:40 PM
    public var basis: PredictionBasis
}
public struct FeedPrediction: Equatable, Sendable {
    public var around: DateInterval          // e.g. 4:15-4:45 PM
    public var basis: PredictionBasis
}

public enum SleepPredictor {
    /// nil while the baby is asleep (running sleep) or there is no wake time to anchor on (no sleep logged yet ->
    /// anchor on now with typicalForAge, clearly labeled).
    public static func next(birthDate: Date, sleeps: [SleepSession], now: Date, calendar: Calendar) -> SleepPrediction?
}
public enum FeedPredictor {
    public static func next(birthDate: Date, feeds: [FeedSample], now: Date, calendar: Calendar) -> FeedPrediction?
}
// Core Data adapter: builds SleepSession/FeedSample arrays for a baby (last 14 days) from a context.
public enum PredictionInputs { public static func load(for baby: Baby, in context: NSManagedObjectContext, now: Date) -> (sleeps: [SleepSession], feeds: [FeedSample]) }
```
Algorithm (keep it explainable):
- **Wake windows**: from the last 14 days, each gap between a sleep's end and the next sleep's start, split
  into daytime gaps by position (1st, 2nd, 3rd... of the day) and the last gap before night sleep. Drop gaps
  outside 0.5x-2x of the age range (bad logs). Use the median per position.
- **Blend**: `personal weight = min(1, samples / 10)`; window centre = weighted mix of personal median and age
  midpoint; clamp the result to the age range widened by 25%. Window width +/-15 min (newborns +/-10 min).
- **Nap vs bedtime**: bedtime when the predicted start is within 90 min of the baby's median night-sleep start
  (last 7 days) or naps-today >= the age's max naps; then the window is centred on the median bedtime
  (blended with the last-wake-window rule).
- **Feeds**: median gap between feed starts (breastfeed + bottle) over the last 3 days, separately for day
  (07-19) and night; blend with the age interval the same way; window +/-15 min.
- Needs >= 3 samples before leaving `typicalForAge`; `personal` when weight == 1.

**As built** (details beyond the spec; all in `Predictions/` and covered by `Predictions*Tests`):
- Age tables are a conservative composite of commonly published ranges (not copied from one source), with the basis
  in a comment on `AgeNorms`. `AgeNorms` also has `typicalBedtime`, `minimumNightSleep` and `ageDays`.
- Cleaning (`SleepHistory`): sleeps closer than 15 min are merged (a brief waking), finished sleeps under 10 min
  are ignored. A *night sleep* starts 17:30-05:30 (evening starts must last 3 h, 2 h under 4 months). Gaps between
  night sleeps are night wakings, not wake windows. The morning wake is a night sleep ending 04:00-11:00.
  All clock reads go through the caller's `Calendar`, so DST days stay on local time.
- Outlier gaps still use up their position in the day, so one missed nap doesn't shift later positions. A position
  with under 3 samples falls back to all daytime windows pooled.
- Nap vs bedtime: "naps today >= cap" uses the baby's own median naps/day (from >= 3 recent days) before the age
  maximum, so a 2-nap baby gets bedtime after nap 2. Bedtime centre = usual bedtime (>= 3 evenings in the last 7)
  weighted 50% with the wake-window rule; a typical-for-age bedtime only weighs 25%.
- No prediction while asleep or during a night waking. If the window closed over an hour ago the log is probably
  missing a sleep: a nap is then counted from now (`lastWake == nil`, `typicalForAge`), a bedtime is dropped.
  Windows that closed less than an hour ago stay and show "overdue". Feeds are dropped after the same hour.
- `PredictionInputs` also exposes `fetchRequest` / `samples(from:now:)` (the Today card is a `@FetchRequest`, no
  manual observing) and `predictions(for:in:now:)` (the widget snapshot).
- `PredictionText` holds the disclaimer, the "how it works" paragraph, basis captions ("Based on Juniper's last 7
  days" / "Typical for 7 weeks, tuned to Juniper's last 5 days" / "Typical for 7 weeks"), age labels and the
  "in 25m" / "now" / "overdue" timing, so the app and tests share the wording.
- Widgets: `nextSleep` is written only when it counts from a real wake-up (a window counted from "now" would change
  on every rewrite). The widget timeline gets one extra entry where each stored window stops being shown (end + 1 h),
  so stale windows disappear with no reload.
- `App/Support/DebugSampleHistory.swift` (DEBUG only): `-lblSeedHistory [-lblSeedAgeDays N] [-lblSeedAsleep]`.

## Reminders (local notifications, per device)

No server: everything is `UNUserNotificationCenter` on each phone. Each caregiver chooses their own reminders,
stored per device (UserDefaults via a `Codable` settings blob, keyed by baby uuid), never synced.

- **Feed every N hours** (per baby): interval 1h-6h in 15-min steps, measured from the start (default) or end of
  the last feed; optional quiet hours. One pending request per baby (fixed identifier) replaced whenever feeds
  change: after every save and every iCloud remote change (`AppServices` already has both hooks), so a feed
  logged on a partner's phone moves my reminder too. If the next time is already past, schedule nothing until
  the next feed. Body: "It's been 3h since Juniper's last feed (Right side). Next: Left".
- **Daily reminders** (per baby, any number): time of day + label + kind (feed / medicine / custom), repeating
  `UNCalendarNotificationTrigger`. E.g. "Vitamin D drops, 9:00 AM".
- **Nap window reminder** (opt-in per baby, uses `SleepPredictor`): lead time 5 / 10 / 15 / 20 min (default 10),
  "Juniper's nap window opens in 10 min (2:10 - 2:40 PM)", rescheduled like the feed reminder. Optional "Also remind
  for bedtime" (default off). Details under "Implementation notes (Reminders)" > Nap window.
- Notification actions: feed reminders get "Start Left" / "Start Right" / "Snooze 15 min" (handled in the app via
  `WidgetActions`, no UI launch for start/snooze) and tapping opens Today. Category identifiers live in BabyLogKit.
- Feed reminders use `.timeSensitive` interruption level (entitlement
  `com.apple.developer.usernotifications.time-sensitive`, free) so they get through Focus / Sleep mode; daily
  medicine reminders too; nap reminders `.active`. Ask for notification permission the first time a reminder
  is turned on (not at launch).
- Battery: local notifications cost nothing at rest; no polling. No BatteryImpactNote needed.

### Implementation notes (Reminders)

**BabyLogKit `Reminders/` (pure, tested in `RemindersPlannerTests` / `RemindersSettingsTests`).**
- `ReminderSettings.swift`: `BabyReminderSettings { feedEvery: FeedIntervalReminder, daily: [DailyReminder] }`, all
  `Codable` with forgiving decoding (every field defaults, unknown kinds fall back) so a later build can add the nap
  reminder without losing saved data. `QuietHours` wraps `NightSchedule` (wraps midnight, start == end is empty).
  `ReminderSettingsStore` keeps one JSON blob `[babyUUID: settings]` in `UserDefaults` (key `reminderSettings`).
- `ReminderPlanner.plan(babies:now:calendar:) -> [ReminderRequest]`: plain values (identifier, title, body, category,
  `ReminderUrgency` `.active | .timeSensitive`, `ReminderTrigger` `.date(Date) | .daily(hour:minute:)`, userInfo).
  - Feed interval: due = start (or end) of the last feed + interval; if that falls in quiet hours it moves to the
    end of the window; a due time that is already past (after the quiet-hours move) plans nothing, so a reminder
    held back until 7:00 survives refreshes at 1:00. A running nursing timer anchors on its start; anchored on the
    end there is nothing until it finishes. A bottle is an instant (end = start). Solids don't count.
  - One-off requests are absolute dates (the app schedules a time-interval trigger, so DST and time-zone changes
    can't shift them); daily ones are wall-clock calendar triggers (the system follows DST).
  - Identifiers: `lbl.reminder.feed.<baby>`, `lbl.reminder.daily.<baby>.<reminder>`, `lbl.reminder.snooze.<baby>`.
    **Adding a reminder type** (nap window): its settings in `BabyReminderSettings`, inputs on `ReminderBaby`, a
    `...Request(for:now:calendar:)` helper, one line in `ReminderPlanner.requests(for:now:calendar:)`, an identifier.
    `ReminderScheduler` needs no change (it replaces by identifier and removes whatever is no longer planned).
  - `snooze(...)` builds the 15-minute copy (feed reminders reword their elapsed time); `isStale(userInfo:babies:)`
    retires delivered / snoozed feed reminders once a newer feed is logged, the feed reminder is off, or the baby is gone.
  - Category and action identifiers (`ReminderCategory`) live here rather than in `Shared/`: only the app uses them.
- **Nap window (as built).** `NapWindowReminder { isEnabled = false, leadMinutes = 10, includeBedtime = false }` is
  `BabyReminderSettings.napWindow` (forgiving decoding: an older blob, or a malformed `napWindow`, reads as off with
  defaults); it counts in `hasAnythingEnabled`, so turning it on asks for notification permission. `ReminderBaby` gained
  `birthDate` and `sleeps`, and the planner calls `SleepPredictor.next` itself (so the planner stays pure and the tests
  use the real predictor); `ReminderInputs.load(in:settings:now:)` reads the sleeps only for babies with the reminder
  on. `napWindowRequest` plans one request, identifier `lbl.reminder.nap.<baby>`, `.active`, no category (a tap opens
  Today), `.date(window.start - lead)`, title "Nap window coming up" / "Bedtime coming up", body "Juniper's nap window
  opens in 10 min (2:10 - 2:40 PM)" (`PredictionText.clockRange`, in the calendar's time zone and the locale's style).
  Nothing is planned when: the baby is asleep or in a night waking (predictor returns nil, so starting a sleep removes
  the pending request at the next refresh), the prediction has no `lastWake` (a window counted from "now" or after a
  stale window would only slide away), the prediction is a bedtime and "Also remind for bedtime" is off (this is the
  "never remind between bedtime and morning wake" rule: naps are never predicted that late, and bedtime is opt-in),
  or `window.start - lead` is not after now (including a window closer than the lead, an open window, or an overdue
  one). The text says "in N min" from the lead, not from the time of planning, so a refresh doesn't rewrite it.
  Same refresh triggers as feed reminders; no scheduler change. The settings screen has a "Naps" section (toggle, "Remind
  me N min before", "Also remind for bedtime"); DEBUG builds add a 1-minute lead. DEBUG seed option
  `-lblSeedWindowInMinutes N` (with `-lblSeedHistory`) places today's last wake-up so the next window opens N minutes from now.
  Not done: a delivered nap reminder isn't retired when a sleep starts (only pending ones are removed).
- `ReminderInputs.load(in:settings:)` is the Core Data adapter (latest breastfeed/bottle per baby; ignores the
  empty nursing placeholder the timer screen creates).

**App.**
- `ReminderScheduler` (`App/Support`, `@MainActor`): reads inputs on its own background context, plans, then diffs
  against `pendingNotificationRequests()`: removes unplanned `lbl.reminder.*` requests, adds only requests that
  differ (content, interruption level, trigger), clears delivered notifications that are stale. Serialized and
  coalesced (a call during a run makes it run once more). Skips scheduling unless notifications are authorized.
  `AppServices` calls `refresh()` after saves, remote changes, `syncNow` (launch, background, intents), and on becoming
  active; the settings screen calls it after each edit. Permission is requested the first time something is turned
  on (`requestPermissionIfNeeded`).
- Notification actions: `AppDelegate` is the `UNUserNotificationCenterDelegate` (set in `didFinishLaunching`, so a
  cold launch from a tap isn't lost; also shows banners while the app is open). `ReminderResponder` handles them:
  Start Left / Start Right use `WidgetActions.nursing` on the app's store (an already-running side is left alone,
  not paused), save, run `AppServices.syncNow(.intent)` and hold a short background task so CloudKit can export;
  Snooze schedules the snooze request; a tap parks `DeepLink.today` in `DeepLinkRouter`, which `RootView` consumes
  (also when the link was produced before the view existed).
- `RemindersSettingsView` (Settings > Reminders): per baby, "Remind me to feed" (every N, counting from start / end,
  quiet hours), "Nap window reminder" (lead time, bedtime sub-toggle) and the daily list (add / edit sheet, enable toggle, swipe to delete). A denied permission shows how to
  turn it on with an "Open iOS Settings" button. DEBUG builds add a 1-minute interval. Night themed.
- Entitlement `com.apple.developer.usernotifications.time-sensitive` is in both app entitlement files (not the widget).
- DEBUG launch arguments (`DebugHooks`): `-lblTestFeedReminder <seconds>`, `-lblTestDailyReminder <minutes>`,
  `-lblClearReminders`; `ReminderScheduler.logPending` logs every pending / delivered reminder
  (`xcrun simctl spawn booted log stream --predicate 'category == "reminders"'`).

## iCloud sync status and friendlier errors

- `CloudSyncProblem.classify(_:)` (BabyLogKit `Sync/`, tested): walks the whole error chain (Core Data's "mirroring
  delegate" wrapper, underlying and partial errors) for the most actionable CloudKit / URL cause and returns a kind
  (`notSignedIn`, `restricted`, `offline`, `storageFull`, `busy`, `syncOff`, `other`), a plain-language `message`
  ("Sign in to iCloud in Settings to share.", "You're offline...", "iCloud sync isn't working right now.") and the
  raw `technicalDetails` text.
- `CaregiverRow` shows the message inline with a "Details" disclosure (selectable monospaced text) and Dismiss;
  with no iCloud account it answers at once instead of waiting for CloudKit to fail.
- `CloudSyncStatus` (`App/Support`, `@Observable`, started from `AppServices`): the "iCloud sync" row in Settings
  (Syncing / Up to date / Not signed in / Unavailable / Error / Off in this build). Event driven:
  `NSPersistentCloudKitContainer.eventChangedNotification` (in-flight set, last success, one error per event type) and
  `CKContainer.accountStatus()` read at launch, when the app becomes active, and on `.CKAccountChanged`. No polling.

## Building

```
brew install xcodegen
xcodegen generate
open LittleBabyLog.xcodeproj
```
Runs in the simulator with iCloud off (the App Group works there without a team). To enable sync/sharing (paid Apple
Developer account required): copy `Config/Local.xcconfig.example` → `Config/Local.xcconfig`, set `DEVELOPMENT_TEAM` and
`BUNDLE_ID_PREFIX`, regenerate. On a real device the App Group `group.<prefix>.littlebabylog` must be registered for your
team too (Xcode does it under Signing & Capabilities > App Groups). Before App Store release, deploy the CloudKit schema
to Production in the CloudKit Console.

Package tests: `cd Packages/BabyLogKit && ./test.sh`.
